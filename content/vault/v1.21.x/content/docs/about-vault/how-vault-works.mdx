# Como o Vault funciona

O Vault é um sistema de gerenciamento de segredos e criptografia baseado em
identidade que centraliza o gerenciamento de segredos, rotaciona credenciais
antigas, gera credenciais sob demanda, audita as interações do cliente e oferece
suporte à conformidade regulatória.

Ele fornece serviços de criptografia protegidos por métodos de autenticação e
autorização para garantir acesso seguro, auditável e restrito a _segredos_.

Um segredo é qualquer coisa cujo acesso você queira controlar rigorosamente,
como tokens, chaves de API, senhas, chaves de criptografia ou certificados.
O Vault fornece uma interface unificada para qualquer segredo, ao mesmo tempo
que oferece controle de acesso rigoroso e registra um log de auditoria
detalhado.

Chaves de API para serviços externos, credenciais para comunicação em
arquitetura orientada a serviços, etc.
Pode ser difícil entender quem está acessando quais segredos, especialmente
porque isso pode ser específico da plataforma.
Adicionar recursos como rotação de chaves, armazenamento seguro e registros de
auditoria detalhados é praticamente impossível sem uma solução personalizada.
É aí que o Vault entra em ação.

O Vault valida e autoriza clientes (pessoas usuárias, máquinas, aplicações)
antes de conceder acesso a segredos ou dados confidenciais armazenados.

## Fluxo de trabalho principal do Vault

O Vault funciona principalmente com tokens associados a uma política de cliente.
A política baseada em caminho define regras que restringem as ações e a
acessibilidade dos caminhos associados para cada cliente.

Os clientes podem se autenticar no Vault para fazer login e obter um token
automaticamente, ou você pode criar tokens manualmente e atribuí-los
explicitamente aos seus clientes.

![Fluxo de trabalho do Vault](/img/vault-workflow-diagram1.png)

O fluxo de trabalho principal do Vault consiste em quatro etapas:

- **Autenticação:** A autenticação no Vault é o processo pelo qual um cliente
  fornece informações que o Vault usa para determinar se ele é quem diz ser.
  Assim que o cliente é autenticado por um método de autenticação, um token é
  gerado e associado a uma política.
- **Validação:** O Vault valida o cliente em relação a fontes confiáveis de
  terceiros, como GitHub, LDAP, AppRole e outras.
- **Autorização:** O cliente é comparado com a política de segurança do Vault.
  Essa política é um conjunto de regras que define a quais endpoints de API um
  cliente tem acesso com seu token do Vault.
  As políticas fornecem uma maneira declarativa de conceder ou negar acesso a
  determinados caminhos e operações no Vault.
- **Acesso:** O Vault concede acesso a segredos, chaves e recursos de
  criptografia emitindo um token com base nas políticas associadas à identidade
  do cliente.
  O cliente pode então usar seu token do Vault para operações futuras.

## A barreira de criptografia

O diagrama abaixo ilustra as complexidades e os componentes distintos do Vault.

[![Visão geral da arquitetura](/img/layers.png)](/img/layers.png)

A camada de criptografia do Vault, chamada de _barreira_, é responsável por
criptografar e descriptografar os dados do Vault.
Quando o servidor Vault é iniciado, ele grava dados em seu backend de
armazenamento.
Como o backend de armazenamento reside fora da barreira, ele é considerado não
confiável, portanto, o Vault criptografa os dados antes de enviá-los para o
backend de armazenamento.
Esse mecanismo garante que, se um invasor malicioso tentar obter acesso ao
backend de armazenamento, os dados não poderão ser comprometidos, pois
permanecerão criptografados até que o Vault os descriptografe.
O backend de armazenamento fornece uma camada de persistência de dados durável,
onde os dados são protegidos e disponíveis mesmo após reinicializações do
servidor.

Quando um servidor Vault é iniciado, ele começa em um estado _selado_.
Antes que qualquer operação possa ser realizada no Vault, o _selo deve ser
retirado_.
Isso é feito fornecendo as chaves de retirada de selo.
Durante a inicialização do Vault, ele gera uma chave de criptografia, usada para
proteger todos os dados do Vault.
Esta chave é protegida por uma chave raiz armazenada com todos os outros dados
do Vault, mas criptografada por outro mecanismo: a chave de retirada de selo.

Por padrão, o Vault usa o
[Compartilhamento de segredo de Shamir](https://en.wikipedia.org/wiki/Shamir%27s_Secret_Sharing)
para dividir a chave de retirada de selo em um número configurado de fragmentos
(partes da chave ou chaves de retirada de selo).
Um número preciso de fragmentos é necessário para reconstruir a chave de
retirada de selo, que é então usada para descriptografar a chave raiz do Vault.

![Chaves de retirada de selo](/img/vault-shamir-seal.png)

Consulte a documentação de
[Selar/Retirar selo](/vault/docs/concepts/seal#seal-unseal) para obter mais
detalhes.

O número de partes e o número mínimo de fragmentos necessários podem ser
especificados.
A técnica de Shamir pode ser desativada e a chave raiz pode ser usada
diretamente para a retirada de selo.
Assim que o Vault recupera a chave de criptografia, ele descriptografa os dados
no backend de armazenamento e entra no estado _sem selo_.
Uma vez sem selo, o Vault carrega os dispositivos de auditoria, os métodos de
autenticação e os mecanismos de segredos configurados.

**Nota:** A configuração padrão do Vault usa um selo de Shamir; no entanto, o
Vault pode ter o
[selo retirado automaticamente](/vault/docs/concepts/seal#auto-unseal) por um
sistema de gerenciamento de chaves na nuvem (KMS) ou módulo de segurança de
hardware (HSM) confiável para aumentar a segurança.

A configuração dos dispositivos de auditoria, métodos de autenticação e
mecanismos de segredos é sensível à segurança e é armazenada no Vault.
Pessoas usuárias com permissões podem modificá-los e não podem ser especificadas
fora da barreira.
Ao armazená-los no Vault, as alterações são protegidas pelo sistema de ACL e
rastreadas por logs de auditoria.

As requisições podem ser processadas da API HTTP para o núcleo assim que o selo
do Vault for retirado.
O núcleo gerencia o fluxo de requisições pelo sistema, aplica ACLs e garante que
o registro de auditoria seja feito.

Quando um cliente se conecta ao Vault pela primeira vez, ele precisa se
autenticar.
O Vault fornece métodos de autenticação configuráveis e oferece flexibilidade no
mecanismo de autenticação usado.
Mecanismos como nome de usuário/senha ou GitHub podem ser usados para pessoas
operadoras, enquanto aplicações podem usar chaves públicas/privadas ou tokens
para se autenticar.
Uma requisição de autenticação que flui pelo núcleo e para um método de
autenticação determina se a requisição é válida e retorna uma lista de políticas
associadas.

Políticas são apenas regras ACL nomeadas.
Por exemplo, a política "root" é integrada e permite acesso a todos os recursos.
Você pode criar qualquer número de políticas nomeadas com controle granular
sobre os caminhos.
O Vault opera em um modo de acesso permitido, o que significa que a ação não é
permitida a menos que o acesso seja concedido explicitamente por meio de uma
política.
Como um usuário pode ter várias políticas associadas, as ações são permitidas
quando a política permite.
As políticas são armazenadas e gerenciadas por um repositório de políticas
interno.
Este repositório interno é afetado pelo backend do sistema, que está sempre
montado em `sys/`.

Assim que a autenticação ocorre e um método de autenticação fornece um conjunto
de políticas aplicáveis, um novo token de cliente é gerado e gerenciado pelo
repositório de tokens.
Este token de cliente é usado para fazer requisições futuras.
Este método de token é semelhante a um cookie enviado por um site quando uma
pessoa usuária faz login.
Dependendo da configuração do método de autenticação, o token de cliente pode
ter um período de concessão associado a ele e pode precisar ser renovado
periodicamente para evitar a invalidação.

Uma vez autenticado, as requisições são feitas fornecendo o token de cliente.
O token de cliente é usado para verificar o cliente, garantindo que ele esteja
autorizado durante o carregamento das políticas relevantes.
As políticas são usadas para autorizar a requisição do cliente.
A requisição é então roteada para o mecanismo de segredos, que é processado
dependendo do seu tipo.
Quando o mecanismo de segredos retorna o segredo, o núcleo o registra com o
gerenciador de expiração e anexa um ID de concessão.
Os clientes usam o ID de concessão para renovar ou revogar seu segredo.
O gerenciador de expiração revoga automaticamente o segredo se um cliente
permitir que a concessão expire.

O núcleo registra requisições e respostas no agente de auditoria, distribuindo
as requisições para todos os dispositivos de auditoria configurados.
Fora do fluxo de requisição, o núcleo executa atividades específicas em segundo
plano.
O gerenciamento de contratos de concessão é crucial, permitindo que tokens ou
segredos de clientes expirados sejam revogados automaticamente.
Além disso, o Vault lida com casos específicos de falha parcial usando registro
antecipado de transações com um gerenciador de reversão.
Isso é gerenciado de forma transparente no núcleo do sistema e não é visível
para a pessoa usuária.
